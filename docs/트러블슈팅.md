## T-001 · 헤드리스 크롬 `--dump-dom` 이 IndexedDB 작업이 끝나기 전에 화면을 찍는다 · 2026-10-15

- 증상: Playwright 이미지의 `chrome-headless-shell --virtual-time-budget=30000 --dump-dom` 으로 `tools/browser_probe.html#selftest` 를 열면 0.7초 만에 끝나고, 결과 코드가 처음 값(`c=x g=o l=- …`) 그대로였다
- 원인(관찰): 동기 작업과 빠른 `fetch` 는 끝났고 첫 IndexedDB `await` 뒤부터는 돌지 않았다. 가상 시간 예산이 IndexedDB 같은 비동기 입출력을 기다리지 않는 것으로 보인다(⚠️ Chromium 문서로 확인하지 않았다)
- 조치: CDP 로 페이지를 열고 `document.body.dataset.done === "1"` 이 될 때까지 기다리는 `tests/ui/cdp.js`(Node 24 내장 WebSocket, 외부 패키지 없음)로 바꿨다
- 재발 방지: 자동 점검 페이지는 끝나면 `<body data-done="1">` 을 단다(`docs/P1_설계서_Probe.md` 3.5절). 스모크는 그 표지를 기다린다
- 확인: `python3 scripts/browser_smoke.py`

## T-002 · 반입 묶음 검사가 문서용 예시 주소를 외부 URL 로 잡는다 · 2026-10-15

- 증상: `python3 scripts/pack_probe.py --check` → `문제: 외부 URL: mylearner-probe-v1/ai_probe.py 안의 http://192.0.2.10:8000,`
- 원인: 호스트를 뽑는 정규식이 쉼표에서 멈추지 않아 `192.0.2.10:8000,` 전체를 호스트로 봤다
- 조치: 호스트 글자에서 쉼표를 뺐다(`scripts/pack_probe.py`, `scripts/check_probe_html.py`)
- 재발 방지: `tests/integration/py/test_verify_tools.py` 의 `test_external_url_detection` 이 쉼표가 붙은 예시를 본다
- 확인: `python3 scripts/pack_probe.py --check`

## T-003 · 리다이렉트를 끈 urllib 처리기가 깨진 `Location` 에서 `ValueError` 로 멈춘다 · 2026-10-15

- 증상: 서버가 `302` 와 `Location: http://[::1`(닫히지 않은 대괄호)을 주면 `ai_probe.py` 가 `예상하지 못한 오류로 멈췄습니다: ValueError` 로 끝나고 결과 코드가 하나도 나오지 않았다(독립 점검 O-1)
- 원인: `urllib.request.HTTPRedirectHandler.http_error_302` 가 `redirect_request` 를 부르기 **전에** `urlparse(Location)` 을 한다(이 VM `/usr/lib64/python3.9/urllib/request.py` 700줄). `redirect_request` 만 `None` 으로 바꿔서는 막히지 않는다
- 조치: `_NoRedirect` 가 `http_error_301·302·303·307·308` 을 바로 `None` 으로 돌린다 → `HTTPDefaultErrorHandler` 가 `HTTPError` 로 넘겨준다. `classify_redirect` 도 읽지 못하는 `Location` 을 `o`(다른 곳)로 본다
- 재발 방지: Phase 6 의 AI 대리 호출도 같은 처리기를 쓴다(`docs/설계서_Architecture.md` 6절 '비밀'). 시험 `CrashSafetyTest`(`tests/integration/py/test_ai_probe_keyleak.py`)
- 확인: `python3 -m unittest tests.integration.py.test_ai_probe_keyleak`

## T-004 · urllib 가 `NO_PROXY` 의 CIDR·`*.도메인`·`;` 목록을 읽지 못해 평문 http 의 키가 프록시로 간다 · 2026-10-15

- 증상: `HTTP_PROXY` 와 `NO_PROXY=localhost,127.0.0.1,.corp.example,127.0.0.0/8` 이면 `127.0.0.0/8` 안의 주소도 프록시로 가서, 호출 10건이 모두 프록시를 지났고 키를 실은 호출도 프록시에 보였다(독립 점검 F-02 — 2026-10-15 다시 돌려 확인). `ALL_PROXY` 만 있으면 urllib 는 프록시를 쓰지 않는데 결과 코드는 `q=p` 였다
- 원인(이 VM 의 CPython 소스로 확인): `proxy_bypass_environment` 는 쉼표로 나눈 뒤 `.` 을 떼고 끝이 같은지만 본다 — CIDR·`*.`·`;`·빈칸 목록을 모른다(`/usr/lib64/python3.9/urllib/request.py` 2538~2546줄). 소문자 `no_proxy` 가 비어 있으면 대문자 `NO_PROXY` 를 지운다(`getproxies_environment`). `ProxyHandler` 는 `all` 키를 쓰지 않는다(800줄 — `all_open` 은 불리지 않는다). Windows `ProxyOverride` 판정(`_proxy_bypass_winreg_override`, 3.11 2631줄)은 호스트에서 포트를 떼고 `fnmatch` 로 비교해 `호스트:포트`·CIDR 항목이 맞지 않고, `<local>` 은 점 없는 이름만 맞는다 ⚠️ Windows 실기에서는 확인하지 않았다
- 조치: 키를 실을 때 평문 http 에 프록시가 걸리면 먼저 프록시 없이 닿는지 보고 직접 연결로 보낸다(`q=k`). 닿지 않으면 키를 보내지 않는다(`e=!p`). 경로 판정(`proxy_applies`)에서 `all` 을 뺐다
- 재발 방지: Phase 6 의 로컬 서버(AI 대리 호출)도 urllib 의 우회 판정을 믿지 않는다(`docs/설계서_Architecture.md` 6절 '비밀'). 시험 `KeyRouteTest`(`CaptureProxy` 가 키를 보지 못함)
- 확인: `python3 -m unittest tests.integration.py.test_ai_probe_keyleak`
